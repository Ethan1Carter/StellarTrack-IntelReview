# StellarTrack-IntelReview

星轨智评（XINGGUI）高校五育综合评价平台，包含 Vue 3 前端和 Express + Sequelize 后端服务。

最新优化：[审核工作台](docs/审核工作台优化说明.md)，支持材料与建议对照、原件页码定位和常用补充意见。后续每轮优化须先备份 GitHub，协作约定见 [AGENTS.md](AGENTS.md)。

后续优化：[规则查询与个性化成长](docs/规则查询与个性化成长说明.md)，支持适用规则原文检索、申报导航、个人偏好预览保存，以及教师调整任务和历史留痕。

第三轮：[材料查重、计分解释与统一待办](docs/查重计分待办优化说明.md)，支持文件指纹和同成果核对、计算过程与只读样本试算、统一待办及临期提醒。

Sites：[独立演示站](https://xinggui-intelreview.ajhz217.chatgpt.site)（所有者私有，使用示例数据），源码位于 `sites/xinggui-demo/`，详见 [交付说明](docs/Sites演示站交付说明.md)。

## 技术栈

- 前端：Vue 3、Vite、Element Plus、Pinia、ECharts
- 后端：Node.js、Express、Sequelize、PostgreSQL

## 本地运行

```bash
npm install
npm run dev
```

后端依赖安装后，可在 `server` 目录运行：

```bash
npm install
npm start
```

请根据实际环境创建 `server/.env`，不要提交生产密钥或数据库凭据。前端环境变量示例见 `.env.development` 和 `.env.production`。

## 注册系统

未登录用户可通过 `/register`（登录页「立即注册」进入）自助注册五类角色：

| 角色 | 注册时需要选择 | 审批人 |
| --- | --- | --- |
| 学生 | 院系 + 班级（班级可自己填新名称） | 无需审批，注册后直接可登录 |
| 班级管理员 | 院系 + 班级（可自己填新名称） | 本班辅导员 |
| 辅导员 | 学校 + 院系 | 该院系的学院管理员 |
| 学院管理员 | **学校** + 院系（可自己填写新院系名） | **该学校的学校管理员** |
| 学校管理员 | **学校** | 超级管理员（超管账号不可自助注册） |

待审批账号无法登录（会提示正在审核）；审批在「组织用户管理 → 角色审批」页面完成，
列表中用「来源」列区分「注册申请」与「角色晋升」。若某角色对应的审批人尚未配置
（例如某班级没有辅导员），注册会被拒绝并给出明确提示，不会产生无人可审的账号。
仍是待审批状态的账号也不能作为审批人（否则会出现"待审批的校管去审批院管"的死循环）。

学院管理员的"所属院系"支持直接输入：本院系还没录入系统时，申请人自己填名称即可，
系统会在该校下新建该院系（代码带 `AUTO_` 前缀便于识别）。若同名院系已存在则直接复用，
不会重复创建；若这次注册被驳回且该院系没有任何成员、也没有下级班级，院系会随驳回一并回收。

学生 / 班级管理员的"所属班级"同样支持直接输入：新班级会挂在所选院系下，
名称里带 4 位年份时（如"2025级软件工程1班"）会自动填成年级；同名班级直接复用。
注意班助注册仍需要该班已有辅导员作为审批人——手填的新班级没有辅导员，
注册会被明确拒绝，且新建的班级会随事务回滚，不会留下空班级。

### 学校层级

学校是组织架构的顶层：`schools` 表 + `users.school_id` + `colleges.school_id`。
超级管理员可在「组织用户管理 → 学校管理」维护学校；院系在「组织架构」里选择所属学校。
学院管理员的审批人会按学校隔离——只有本校的学校管理员能收到并处理该申请。

「组织架构」页为 **院系 → 辅导员 → 班级** 三栏：左栏选院系，中栏列出该院系的辅导员
（含各自所带班级数），点击某位辅导员即可把右栏班级列表筛成"他所带的班"；
专业不再单独维护，直接在班级的新增/编辑弹窗里选择或输入即可。

已有数据库升级：`psql -h 127.0.0.1 -U postgres -d <库名> -f server/scripts/migrate-add-schools.sql`
（可重复执行：建表用 IF NOT EXISTS，只回填 `school_id IS NULL` 的历史数据，不覆盖已有归属）。

学校管理员按本人 `school_id` 限制到本校院系、班级和用户；未绑定学校时拒绝访问业务数据。
查询、计数、聚合和写操作还通过请求内的学校边界做统一约束，防止旧接口遗漏筛选条件。
平台通用模块、默认公式和学期可读，由超级管理员维护；学校管理员创建学期时，默认面向本校院系。
数据库备份和恢复属于平台操作，仅超级管理员 / 开发者可用。

### 辅导员维护"我带的班级"

辅导员登录后可在「我的班级 → 我带的班级」（`/my-classes`）自己维护所带班级：

- **新增班级**：只能建在本人所属院系，后端强制 `counselorId = 本人`、`collegeId = 本人院系`，建完即归到自己名下。
- **认领已有班级**：列出本院系下 `counselor_id` 为空且状态启用的班级，认领后归到自己名下；
  只能认领本院系、且班级必须还没有辅导员（并发用行锁 + 二次校验，避免两个辅导员抢同一个班）。
- 「我的班级」详情页支持 `?classId=` 指定查看名下的某个班（辅导员可带多个班）。

相关开关见 `server/.env`：`REGISTRATION_ENABLED`（是否开放注册）、
`REGISTRATION_RATE_MAX`（同 IP 每小时注册上限，0 表示不限制）。

回归自检（后端启动后运行，两条脚本都会自建所需链路、结束时打印清理 SQL）：

```bash
cd server
node scripts/_test-register-flow.js         # 注册全链路 43 项
node scripts/_test-school-register-flow.js  # 学校绑定与分校审批 28 项
```

## 日常检查与本轮完善

在项目根目录运行 `npm test`，执行前端行为、后端权限、上传、Excel 导入和部署清单回归；
这些新测试使用模拟数据，不连接日常数据库。`npm run build` 检查前端生产构建。

附件需要登录后访问，浏览器通过仅限 `/uploads` 的 HttpOnly Cookie 预览图片及 PDF。
部署时应将 `/api` 和 `/uploads` 代理到同一后端，不能额外公开映射上传目录。
新附件目录由鉴权用户决定；旧材料按已有申报、申诉或公告关联核验，无法证明归属时需重新上传。

测试部署包仅保留环境变量示例，并生成同源 `/api` 的前端配置。可先运行
`powershell -File deploy/package-test.ps1 -ListOnly` 查看文件清单。

详细改动、部署条件和待完善范围见 [本轮完善与验证说明](docs/完善与验证说明.md)。

## 参赛版本：材料证据与成长行动

材料审核支持图片及 PDF 逐页识别、获奖人身份核对、附件页码和评分规则原文引用。
成长行动计划在 `/growth-plan` 提供学生记录、教师反馈及过程历史，建议来源明确标注为规则辅助。

升级已有数据库时，在 `server` 目录执行 `npm run migrate:growth-plans`，只创建成长计划新表，不改变原有业务表。
PDF 识别需安装 Poppler 的 `pdfinfo` 和 `pdftoppm`，可用 `npm run check:ai-runtime` 检查；绝对路径配置见 `server/.env.example`。
升级后重启后端并刷新前端。真实 PostgreSQL 的随机隔离 schema 验证可运行 `npm run test:growth-db`，不会修改现有师生和评价数据。

完整能力边界、验证结果和比赛演示顺序见 [参赛版本更新说明](docs/参赛版本更新说明.md)。
