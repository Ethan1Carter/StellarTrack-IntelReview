## 已确认问题

### P1：班级管理员可以初审自己的申报并即时计分

隔离库中以班级管理员本人提交一条 3 分申报，再以同一账号调用初审接口，返回 HTTP 200「已通过」，本人的学期分数变为 3。后续辅导员终审仍是另一环节，但初审阶段已经由本人完成且分数已入账。

代码依据：`server/routes/applications.js` 的 `approveHandler` 校验审批节点，但缺少申请人与审核人为同一账号的拒绝；`src/components/ApprovalList.vue` 的 `canApprove` 仅判断申报状态，未排除本人。

处理建议：明确本人申报的替代审核人或流转规则，同时在界面、单条审核、批量审核和后端计分入口拒绝自审，验证不会形成无人可处理的死单。

### P2：用户管理按钮与后台权限不一致

辅导员界面允许点击「新增用户」，用户行同时显示「编辑、重置密码、删除」；班级管理员的用户行也显示维护操作。实际接口中，辅导员新增用户返回 403，班级管理员与辅导员编辑用户也都返回 403。

代码依据：`src/views/manage/Users.vue` 的 `canCreate` 包含辅导员，行操作缺少对应权限控制；`server/routes/users.js` 的新增、编辑与删除接口要求院管及以上。后台虽保留辅导员编辑分支，但会先被角色守卫拦截。

处理建议：按最终职责明确辅导员是否能维护所带班级用户，再统一按钮、路由与接口权限。班级管理员不应看到不可执行的维护按钮。

### P2：部分管理接口仅允许院管，校管与超管反而被拒绝

同一组合成学生账号的密码重置结果：院管 HTTP 200，校管 403，超管 403，开发者 200。用户导入模板下载也出现相同差异。开发者成功来自额外的开发者放行，不能证明超管正常。

代码依据：`server/routes/users.js` 的密码重置与导入模板接口使用精确的 `requireCollegeAdmin`，没有采用院管及以上的分组。用户界面却显示相应管理操作。

处理建议：统一管理角色层级，同时保留本院、本校、全平台的数据范围；扩展角色入口时一并校验目标账号等级，避免低级管理员操作更高权限账号。
