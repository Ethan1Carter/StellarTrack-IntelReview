# 制度与活动 503 修复记录

日期：2026-10-21。

## 原因与处理

本机原业务系统已更新前后端源码，但 PostgreSQL 缺少 `guidance_resources` 表，制度目录和校园活动接口因此返回 HTTP 503。前端又将后端的升级说明覆盖为笼统的「服务器错误（503）」。

修复前已将源码推送到独立 GitHub 备份分支 `codex/backup-before-guidance-503-fix-20261021063047`，核验远端提交为 `8643bf3bdf5509e6e0f6dfaa01a0fccfd40a42b5`。

在用户同意按修复步骤处理后，先以 PostgreSQL `pg_dump` 完整备份本机业务数据库，保存在 Git 忽略的 `server/backups/` 目录；以 `pg_restore --list` 核验归档可读并记录 SHA-256。此项属于归档校验，未执行恢复演练。数据库备份、配置、日志和真实账号截图均不上传 GitHub。

随后以 `alter:false, force:false` 只创建缺失的新表，未插入示例数据；对比迁移前后，原有 22 张表的行数保持一致。没有重建旧表或修改师生记录，也没有重新发布原系统生产服务。

## 源码修复

- 迁移入口按脚本位置加载 `server/.env`，避免从项目根目录运行时因找不到环境配置而失败；仍要求显式传入 `--apply`。
- 后端为数据表未启用返回稳定的 `GUIDANCE_STORAGE_NOT_READY` 状态；前端只对该状态显示升级指引。其他服务器错误仍使用通用提示，避免暴露内部详情。
- 新增 `server` 目录下的 `npm run migrate:guidance` 命令。其他环境执行前仍需确认目标库、取得升级授权并完成业务数据库备份。

## 验证

- 原项目自动化检查共 69 项通过：前端与部署等检查 28 项、后端 41 项；生产构建通过。
- 缺表时两个真实路由返回可识别的升级状态，空表时正常返回空目录；前端不会展示服务器内部错误详情。
- 迁移命令不带 `--apply` 时拒绝执行；带参数可执行且重复执行成功。
- 在原业务系统已登录浏览器中验证制度目录与活动列表均正常显示；运行日志确认两个接口已由 503 恢复为 200。成长计划入口也正常加载。

当前制度与活动目录为空，需要管理员录入、核对并发布真实校方资料后，学生端才会展示内容。Sites 的虚构示例没有导入业务数据库。
