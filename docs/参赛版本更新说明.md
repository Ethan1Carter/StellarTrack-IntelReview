# 参赛版本更新与验收说明

更新日期：2026-10-19。

## 已完成

### 1. PDF 材料正文与页码

PDF 经 Poppler 转换为逐页图像，再交给已配置的视觉模型读取。文本型与扫描型 PDF 均走完整页面识别；当前没有另外实现原生文本层解析。

- 默认一次最多 5 页，单文件 10MB，配置可调整页数但硬上限为 8 页。
- 完整读取限制内的全部页面，获奖人和事实引用保留页码。
- 超页数直接提示拆分，不以部分页面推断“不属于本人”。
- 文件损坏、加密、组件缺失、超时或页面图像过大时，明确转人工，不根据文件名猜测内容。
- 临时转换文件在识别请求中及时清理，不公开页面中间文件。

### 2. 评分原文与人工修改说明

- 只向模型提供适用于当前账号的模块（院系、年级、专业和班级限制）。
- 模型提供的评分引用必须确实存在于模块的 `ruleDescription`；保存来源、上限、更新信息和规则版本摘要。
- 缺少有效原文引用时，暂停自动分值建议。命中规则原文仍只是辅助建议，教师需判断条件和适用学年。
- 修改 AI 标题、分值等建议，或者使用归属未确认的分析结果正式申报，需要填写人工核对说明。
- 服务端保存原始 AI 结果、修改字段、确认人、时间与说明，浏览器不能伪造原始签名结论。
- 审核中心和申报详情可展开附件事实及评分依据。

模块规则来自管理员当前配置，未自动认证其为学校正式制度。未建立外部官方制度知识库，不宣称实现 RAG。

### 3. 成长行动闭环

入口：侧栏“成长行动计划”，也可从个人数据看板进入。

1. 学生预览当前学年/学期的建议，保存后生成固定任务及期限。
2. 记录执行情况，上传最多 5 份本人证明，保存进度或提交教师核验。
3. 有范围权限的辅导员/院校管理员可以核验完成，或退回补充。
4. 后续补充不会覆盖之前的记录和证明；刷新后保留状态及反馈。

建议明确标注“规则辅助”。只依据当前已记录数据提出行动方向，不将不同量纲的原始分数排序为学生能力高低，也不把缺少记录解读为缺少参与。没有编造具体校园活动名称和报名链接。

原数据看板及导出报告中的模板分析也改为标注“规则辅助”，与材料页的真实模型识别区分。

学生不能自行标记“已核验完成”，不能核验本人，也不能访问同班其他学生的计划。并发保存通过数据库行锁和版本号避免覆盖。任务完成不自动增加综测分数。

## 部署与复测

在 `server` 目录执行：

```text
npm run migrate:growth-plans
npm run check:ai-runtime
```

PDF 组件需随部署环境提供：Linux 可使用发行版的 `poppler-utils`，Windows 将 Poppler 放入 PATH 或在 `.env` 中设置 `AI_PDFINFO_PATH`、`AI_PDFTOPPM_PATH`。建议 Windows 路径使用 `/` 分隔符；生产服务账号必须有执行权限。

新环境执行 SQL 初始化后，同样运行上面的成长表迁移。迁移脚本不执行 `alter` 或 `force`，不改变其他表。完成后重启后端并刷新前端；旧材料要“重新分析”才能取得本轮新字段。

在项目根目录运行 `npm test`、`npm run build`。PDF 转换集成检查需要可执行的 Poppler 组件。

以下为显式验证，会使用所配置的资源：

```text
node server/scripts/ai-ownership-smoke.js --live --pdf
node server/scripts/test-growth-plan-db.js --isolated-schema
```

第一条仅发送合成测试证书并产生一次模型调用；第二条仅在 PostgreSQL 创建并清理随机测试 schema。两条都不读取真实学生材料。

## 建议比赛演示顺序

1. 上传一份本人材料，展示姓名及附件页码。
2. 展示模块规则原文、分值上限和人工修改说明。
3. 上传他人证书，展示归属不符及暂停申报。
4. 进入成长行动计划，展示一条学生记录、教师反馈和历史过程。

下一步仍需按真实学校制度确认模块内容，组织小范围师生试用，记录准确率及耗时，再据实撰写申报文档、录制演示视频。没有实测数据时，不填写效率提升百分比或全校落地人数。
